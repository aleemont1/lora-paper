\begin{abstract}
  This paper presents \ac{LAMP}, a lightweight transport architecture that enables the continuous transfer of large data blocks over point-to-point Long-Range (LoRa\textsuperscript{\textregistered}) networks. To overcome the prohibitive Time-on-Air overhead and duty-cycle saturation typical of existing Stop-and-Wait solutions, the proposed architecture segments payloads into up to 255 chunks per transmission window. Each chunk is protected by a 9-byte Logical Header with compact 8-bit node addressing (supporting downstream IPv6 link-local prefix mapping) and a 2-byte \ac{CRC}-16 checksum suffix. The protocol provides four distinct operational modes combining connection state (Connectionless / Stateful) and reliability (Best-effort / {SACK}-{ARQ} feedback). By requiring receiver feedback only at sequence boundaries rather than per-packet, the \ac{SACK} mechanism significantly reduces acknowledgment overhead without incurring the constant over-the-air encoding overhead of pure \ac{FEC}.
\end{abstract}

\IEEEPARstart{L}{ow-power}, low-cost, and long-range wireless communication technologies
are becoming increasingly important in the context of the \ac{IoT}. Applications
such as environmental monitoring, precision agriculture, and autonomous \acp{UAV} require
reliable data transmission over extended distances under strict power and hardware
constraints~\cite{10807074}.

Several communication standards, including ZigBee, Sigfox, and \ac{LoRa}
have been adopted to address these needs, and \ac{LoRa}, in particular, has
emerged as the leading choice for low-power and long-range deployments thanks to
its robust modulation technique and open network architecture~\cite{8424846}.
However, conventional solutions based on \ac{LoRa} (particularly those following
the LoRaWAN\textsuperscript{\textregistered} specifications) are optimized for small, non-frequent payloads~\cite{8016141}.

This limitation poses acute restrictions on data-intensive \ac{IoT} applications which demand the continuous transfer of large data blocks~\cite{multimedia-lora-survey, dare-lorawan}, such as \ac{FUOTA}, \ac{SLAM} map transfers in autonomous robotics, or bulk sensor log collection. Standard \ac{LoRaWAN} links require substantial transmission overhead, restrictive duty-cycle limitations~\cite{etsi300220}, and lack optimized mechanisms for handling large, multi-packet payloads in point-to-point configurations.

This paper presents the design and implementation of \ac{LAMP}, a lightweight transport protocol for point-to-point and local multi-node \ac{LoRa} networks. LAMP supports payloads up to 62.2~KB on 255 byte \ac{FIFO} transceivers (such as the Semtech\textsuperscript{\textregistered} SX1262), operating independently of higher-layer middleware such as \ac{LoRaWAN}.

The main contributions of this work are:
\begin{itemize}
  \item \textbf{Bitmap-Based \ac{SACK} Scheme}: Unlike existing \ac{LPWAN} fragmentation solutions that rely on Stop-and-Wait (S\&W) \ac{ARQ}, which requires one acknowledgment per packet and incurs substantial latency under duty-cycle constraints, the proposed protocol uses a compact binary bitmap carried in a single feedback frame. The receiver reports the delivery status of up to 255 chunks per round-trip, reducing retransmission overhead and over-the-air footprint.
  \item \textbf{Lightweight Packet Segmentation and Abstraction}: The protocol introduces a 9-byte logical header (with 8-bit local node addressing) and a custom \ac{CRC} integrity check on partial payloads, enabling out-of-order chunk reassembly on resource-constrained microcontrollers.
  \item \textbf{Modular C++17 Implementation and \ac{TDD} Validation}: The core state machine is completely decoupled from the physical radio driver through a \ac{HAL}. This design enables both native host-based unit testing (using the Unity framework) and physical deployment on Semtech SX126x transceivers.
\end{itemize}

\section{State of the Art and Design Space}
\label{sec:state_of_art}
Reliable packet fragmentation and transport over \acp{LPWAN} has been the subject of extensive investigation, driven by the expanding demand for data-intensive \ac{IoT} workloads~\cite{multimedia-lora-survey, dare-lorawan}. Existing approaches broadly fall into three categories: standardized LPWAN frameworks, conventional Stop-and-Wait ARQ, and specialized windowed batch transports.

\subsection{Standardized LPWAN Frameworks: SCHC and LoRaWAN TS004}
At the standardization level, the IETF defined \ac{SCHC}~\cite{rfc8724, rfc9011}, introducing a generic architecture for header compression and fragmentation over LPWANs. RFC~9011 defines SCHC profiles over LoRaWAN supporting No-ACK, ACK-Always, and ACK-on-Error modes. While SCHC achieves high compression for predictable IPv6/UDP flows (down to 1--2 bytes), it relies on pre-provisioned static rule contexts and gateway-centric infrastructure, making it ill-suited for autonomous, ad-hoc raw-\ac{LoRa} peer-to-peer or multi-node links. Similarly, the \ac{LoRa} Alliance standardized Fragmented Data Block Transport (\ac{TS004})~\cite{ts004} to support \ac{FUOTA} via open-loop \ac{FEC} redundancy codes. While open-loop \ac{FEC} delivers multicast firmware images without requiring a reverse feedback channel, it introduces continuous over-the-air encoding overhead regardless of physical channel conditions and imposes substantial computational decoding demands on resource-constrained microcontrollers.

\subsection{Point-to-Point Transports and Stop-and-Wait Limitations}
In infrastructure-free point-to-point and local mesh configurations, early implementations relied on Stop-and-Wait (S\&W) \ac{ARQ}. However, empirical link evaluations by Cattani et al.~\cite{cattani2017} and network scalability analyses by Bor et al.~\cite{bor2016} established that per-fragment acknowledgments incur prohibitive Time-on-Air latencies and severe duty-cycle saturation when applied to multi-packet payloads. Under typical LPWAN channels, the round-trip overhead of waiting for an individual ACK after every single packet dramatically reduces effective throughput.

\subsection{Windowed Selective Transports: MPLR and Technical Gaps}
To mitigate Stop-and-Wait overhead, Chen et al.~\cite{mplr-chen2019} proposed \ac{MPLR}, introducing windowed batch transmissions acknowledged by a bit-vector acknowledgment packet (\texttt{BVACK}). While pioneering the use of bitmap feedback over LoRa, MPLR was engineered as an application-specific pipeline tailored strictly for uploading agricultural camera images from an end-device to a central gateway. Consequently, MPLR exhibits key architectural limitations when generalized as a generic transport protocol:
\begin{enumerate}
  \item \textit{Substantial Header Overhead}: MPLR enforces a 16-byte fixed header per fragment (allocating 8~bytes for 64-bit EUI source/destination addresses), which consumes a substantial portion of the 255-byte maximum LoRa physical payload.
  \item \textit{Rigid Single-Mode Operation}: MPLR operates solely under a stateful batch model with a fixed window size (40 packets), lacking support for unacknowledged streaming, connectionless datagrams, or dynamic window scaling.
  \item \textit{Static Setup and Heavy Teardown}: MPLR lacks run-time buffer negotiation and mandates an explicit 4-way handshake teardown sequence (\texttt{FIN}/\texttt{ACK}), generating unnecessary control frame traffic.
\end{enumerate}

\subsection{Architectural Contributions of LAMP}
LAMP addresses these gaps by establishing an autonomous, lightweight, and configurable transport layer operating directly over raw \ac{LoRa} PHY. As summarized in Table~\ref{tab:arch_comparison}, LAMP advances the state of the art through four core design principles:
\begin{itemize}
  \item \textbf{Compact Header Architecture}: LAMP utilizes a 9-byte Logical Header (+2-byte \ac{CRC}-16 suffix, totaling 11~bytes over the air), reducing per-fragment control overhead by 31.2\% compared to MPLR (16~bytes) while providing 8-bit local unicast/broadcast addressing.
  \item \textbf{Four-Mode Operational Flexibility}: Unlike single-mode batch protocols, LAMP spans a complete operational matrix: \textit{Unreliable Connectionless} (Mode 1), \textit{Unreliable Connected} (Mode 2), \textit{Reliable Connectionless} (Mode 3), and \textit{Reliable Connected} (Mode 4).
  \item \textbf{Dynamic 3WHS Negotiation \& Safe Memory Bounds}: Incorporates run-time parameter negotiation (\texttt{SynMetadata}) for buffer safety on low-power microcontrollers, replacing explicit 4-way teardown overhead with automatic idle session pruning.
  \item \textbf{Transport-Layer Purity}: Completely decoupled from physical radio drivers via a clean \ac{HAL}, enabling native host testing and embedded deployment.
\end{itemize}

\section{Proposed System Architecture}
\label{sec:architecture}
LAMP is a transport-layer protocol running directly over the \ac{LoRa} physical layer. It segments arbitrarily large payloads (within the described constraints) at the transmitter and reconstructs them at the receiver while minimizing Logical Header and \ac{OTA} overhead.
\subsection{Protocol Specification and Design Iterations}
We describe the design of LAMP by contrasting its initial stateless baseline (LAMPv1) with the current addressed architecture (LAMPv2).

\subsubsection{Stateless Header Specification}
The initial protocol version, LAMPv1, was designed for maximum header compression during periodic sensor telemetry transfers over point-to-point links. It utilized a compact 7-byte Logical Header containing only sequence tracking and payload bounds (\texttt{messageId} [2~B], \texttt{totalChunks} [1~B], \texttt{chunkIndex} [1~B], \texttt{payloadSize} [1~B], \texttt{flags} [1~B], and \texttt{protocolVersion} [1~B]). 

While LAMPv1 achieved high spectral efficiency for isolated datagram bursts, deployment on embedded hardware revealed three key architectural limitations:
\begin{itemize}
  \item \textit{Speculative Buffer Allocation}: Receivers allocated reassembly memory speculatively upon receiving the first fragment of an unannounced stream. When receiving large payloads (e.g., image tiles or firmware blocks), memory-constrained microcontrollers risked heap exhaustion or buffer overflows.
  \item \textit{Session Interference}: Lacking explicit source and destination identifiers, multiple unaddressed transmitters sharing the same RF channel risked interleaving fragments with identical sequence numbers, leading to corrupted reassembly buffers.
  \item \textit{Static Transport Limits}: Fixed chunk sizes and static timeout thresholds prevented dynamic adaptation to link quality degradation or variable receiver memory limits.
\end{itemize}

\subsubsection{Addressed Logical Header Specification}
To resolve the limitations of LAMPv1, LAMPv2 introduces an addressed, stateful transport architecture. LAMPv2 expands the Logical Header to 9~bytes by embedding explicit 8-bit Source (\texttt{srcAddr}) and Destination (\texttt{dstAddr}) Node Identifiers, while incorporating an integrated \ac{3WHS} mechanism.

Although adding 2~bytes to the header increases over-the-air frame length by less than 0.8\% relative to the maximum 255-byte frame (9-byte header + 244-byte payload + 2-byte \ac{CRC}-16), this trade-off provides three main architectural benefits:
\begin{enumerate}
  \item \textit{Buffer Memory Safety}: The \ac{3WHS} exchange allows nodes to negotiate reassembly buffer limits (\texttt{SynMetadata}) prior to payload transmission, preventing allocation failures on memory-constrained receivers.
  \item \textit{Channel Session Isolation}: Explicit node addressing prevents session crosstalk and frame interleaving in multi-node wireless topologies.
  \item \textit{IPv6 Integration Readiness}: The 8-bit Node ID introduces a lightweight local addressing namespace that can be mapped directly to an IPv6 link-local prefix at an edge gateway, enabling transparent IP-layer integration without transmitting heavy 128-bit IPv6 headers over raw \ac{LoRa} radio links.
\end{enumerate}

\subsection{Operational Modes and Sequence Management}
To accommodate diverse \ac{IoT} workload requirements, LAMP defines four distinct operational modes across two primary dimensions: \textit{Reliability} (Unreliable Best-Effort vs. \ac{SACK}-\ac{ARQ}) and \textit{Connection State} (Connectionless Handshake-Free vs. Connection-Oriented Stateful).

\subsubsection{Implicit Frame Boundary Derivation}
To maintain a compact 9-byte header while supporting robust out-of-order packet reassembly, LAMP avoids dedicated boundary control bits. Instead, Start-of-Message (SOM) and End-of-Message (EOM) boundaries are implicitly derived at the receiver directly from the 0-based fragment index (\texttt{chunkIndex}) and the total fragment count (\texttt{totalChunks}):
\begin{equation}
\mathrm{SOM} \iff \texttt{chunkIndex} == 0
\end{equation}
\begin{equation}
\mathrm{EOM} \iff \texttt{chunkIndex} == \texttt{totalChunks} - 1
\end{equation}
Explicitly carrying \texttt{totalChunks} in every fragment header allows the receiver to determine the exact message bounds and pre-allocate the required reassembly buffer and \ac{SACK} bitmap upon receiving \textit{any} fragment, even if fragments arrive out of order or if the initial chunk is lost.

\subsubsection{Node Addressing Scheme}
To support multi-node communication without incurring the prohibitive airtime overhead of full 128-bit IPv6 headers on \ac{LoRa} PHY payloads, LAMP introduces a compact 8-bit Node Identifier space:
\begin{itemize}
  \item \textbf{\texttt{0x00} (\texttt{ADDRESS\_UNASSIGNED})}: Reserved for legacy or unaddressed P2P datagrams (promiscuous mode).
  \item \textbf{\texttt{0x01}--\texttt{0xFE}}: 254 unique individual node addresses (Unicast).
  \item \textbf{\texttt{0xFF} (\texttt{ADDRESS\_BROADCAST})}: Broadcast address processed by all active receiving nodes on the RF channel.
\end{itemize}
As detailed in Section~\ref{sec:architecture}-A, this 8-bit Node ID maps directly to an IPv6 link-local suffix at edge gateways, enabling IP-layer integration without transmitting 128-bit addresses over the constrained radio link.

The 8-bit address space supports up to 254 unicast nodes per RF cluster, which is sufficient for the dense but bounded deployments targeted by this work (e.g., agricultural sensor arrays, \ac{UAV} swarm sub-clusters). For applications requiring broader network reach, Section~\ref{sec:conclusion} foresees integration of full IPv6 routing, where the 8-bit node identifier serves as a local cluster suffix rather than a global unique identifier. Note that the 254 addressable nodes operate independently of the receiver's concurrency limit ($\texttt{MAX\_CONCURRENT\_SESSIONS} = 10$), which governs the maximum number of simultaneously active reassembly sessions.

The fields in the Logical Header are defined as follows:
\begin{itemize}
  \item \textbf{\texttt{srcAddr} (1 byte)}: Source node identifier (\texttt{0x01}--\texttt{0xFE}, or \texttt{0x00} for unassigned).
  \item \textbf{\texttt{dstAddr} (1 byte)}: Destination node identifier (\texttt{0x01}--\texttt{0xFE}, or \texttt{0xFF} for broadcast).
  \item \textbf{\texttt{messageId} (2 bytes)}: Unique message sequence identifier. All fragments composing the same segmented message share this ID. Active and completed sessions are uniquely keyed by the 4-tuple $(\mathtt{srcAddr}, \mathtt{dstAddr}, \mathtt{messageId}, \mathtt{version})$.
  \item \textbf{\texttt{totalChunks} (1 byte)}: The total count of chunks into which the original large payload is divided ($1 \le \texttt{totalChunks} \le 255$).
  \item \textbf{\texttt{chunkIndex} (1 byte)}: The 0-based index of this specific fragment ($0 \le \texttt{chunkIndex} < \texttt{totalChunks}$).
  \item \textbf{\texttt{payloadSize} (1 byte)}: Payload data byte count ($0 \le L \le 244$~bytes; $L=0$ for pure control frames). On standard SX1262 transceivers (256-byte FIFO, 255-byte maximum PHY frame), subtracting the 9-byte header and 2-byte CRC-16 yields $S_{\max} = 244$~bytes per chunk, resulting in a single-session capacity of $255 \times 244 = 62,220$~bytes ($\approx 62.2$~KB).
  \item \textbf{\texttt{flags} (1 byte)}: A control bitfield used to manage transmission and connection states:
  \begin{itemize}
    \item \texttt{FLAG\_ACK\_REQ} (\texttt{0x04}): Selective Acknowledgment requested from receiver.
    \item \texttt{FLAG\_ACK} (\texttt{0x08}): SACK feedback packet containing binary bitmap of received chunks.
    \item \texttt{FLAG\_CONN\_REQ} (\texttt{0x10}): Connection Request control frame.
    \item \texttt{FLAG\_CONN\_ACK} (\texttt{0x20}): Connection Acknowledged control frame.
    \item \texttt{FLAG\_CONN\_NACK} (\texttt{0x40}): Connection Refused control frame.
  \end{itemize}
  \item \textbf{\texttt{protocolVersion} (1 byte)}: Identifies protocol version (currently 2) to ensure backward compatibility.
\end{itemize}

In LAMPv2, broadcast addressing (\texttt{0xFF}) is strictly restricted to unreliable Best-Effort Datagrams (Mode 1). To avoid acknowledgment implosion and channel collapse, control frames (\texttt{FLAG\_ACK\_REQ}, \texttt{SYN}, \texttt{SYN-ACK}, \texttt{CONN\_NACK}) are prohibited with \texttt{dstAddr = 0xFF}.

After the payload, a 16-bit CRC-16 (Modbus CRC-16, polynomial \texttt{0xA001}, initialized to \texttt{0xFFFF}) is appended. The checksum is computed over the concatenation of the 9-byte Logical Header and exactly \texttt{payloadSize} application-layer bytes; any trailing buffer bytes beyond \texttt{payloadSize} are excluded, so that partial final chunks are validated identically to full-size chunks and inter-implementation interoperability is preserved.

\subsection{Selective Acknowledgment and Retransmission}
In reliable mode, the protocol implements a \ac{SACK} mechanism~\cite{lora-arq-sar} to recover lost fragments with minimal additional airtime.

\subsubsection{Retransmission Protocol Interaction}
When a transmission is executed in reliable mode:
\begin{enumerate}
  \item The transmitter segments the payload, serializes the chunks with \texttt{srcAddr} and \texttt{dstAddr}, and streams them sequentially. The final chunk index ($Index = \texttt{totalChunks} - 1$) is marked with the \texttt{FLAG\_ACK\_REQ} flag.
  \item Upon receipt of the chunk requesting acknowledgment, the receiver evaluates its reassembly session. It identifies which fragments are still missing by checking its internal bitmask of received chunks.
  \item The receiver responds by transmitting a \ac{SACK} packet (\texttt{FLAG\_ACK}) addressed back to the transmitter's \texttt{srcAddr}. The \ac{SACK} carries a payload of $\lceil N/8 \rceil$ bytes containing a binary bitmap: chunk index $i$ ($0 \le i < N$) maps to bit position $(i \bmod 8)$ of byte $\lfloor i/8 \rfloor$ (LSB-first ordering), where a 1-bit indicates successful reception and a 0-bit indicates a missing fragment.
  \item The transmitter parses the received \ac{SACK} bitmap. If some chunks are missing, it selectively retransmits only those lost chunks. The last retransmitted chunk has the \texttt{FLAG\_ACK\_REQ} flag set again to query the receiver.
  \item This selective retry loop continues until the full message is reconstructed at the receiver, or the transmitter reaches the maximum retry count.
\end{enumerate}

\subsubsection{Half-Duplex Hardware Switching Guard}
Because \ac{LoRa} transceivers are half-duplex, a hardware transition period is required for the transmitter to switch from transmit (TX) mode to receive (RX) mode after sending a packet. While physical SX1262 transceiver state transitions take $<100\,\mu\text{s}$, the $\delta = 25$~ms guard delay accounts for physical transceiver switching alongside software-level Real-Time Operating System (RTOS) task scheduling jitter, Serial Peripheral Interface (SPI) bus transaction queuing, and microcontroller wake-up latencies on embedded targets.

It is important to emphasize that all protocol timing parameters, guard delays (e.g., \texttt{SACK\_PREAMBLE\_GUARD\_DELAY\_MS}), and retry limits are fully decoupled into a centralized configuration namespace (\texttt{LoRaMultiPacketConfig}) and can be customized by integrators for any MCU/radio target. The default parameters presented in this study were specifically tuned around the Heltec Wi-Fi \ac{LoRa}~32~V3 (ESP32-S3) hardware platform.

\subsubsection{Timeout and Fallback Recovery}
If the transmitter does not receive a \ac{SACK} packet within the dynamic timeout window, it assumes the query or response was lost and retransmits the last transmitted chunk with the \texttt{FLAG\_ACK\_REQ} flag. The transmitter permits up to $R_{\mathrm{max}} = 5$ consecutive timeout events before aborting the session.

The timeout is computed adaptively to account for forward data frame airtime, receiver turnaround, and reverse \ac{SACK} airtime:
\begin{equation}
T_{\mathrm{timeout}} = \max\!\left(T_{\min},\;\alpha\cdot\left(\widehat{T}_{\mathrm{oA, DATA}} + \widehat{T}_{\mathrm{oA, SACK}}\right) + \delta\right)
\label{eq:timeout}
\end{equation}
where $T_{\min} = 1000$~ms is the minimum guard, $\alpha = 1.5$ is a safety factor, $\widehat{T}_{\mathrm{oA, DATA}}$ and $\widehat{T}_{\mathrm{oA, SACK}}$ are the Times-on-Air for the data frame and reverse \ac{SACK} frame queried from the radio driver~\cite{semtech-an1200}, and $\delta = 25$~ms is the half-duplex switching and scheduling guard delay. Table~\ref{tab:timeouts} reports representative timeout values across spreading factors.

\subsubsection{Idealized Analytical Burst Reliability Baseline}
Under an independent frame loss probability $p$ and assuming error-free control feedback, the probability that an individual chunk fails after $R_{\mathrm{max}}$ repair rounds is $p^{R_{\mathrm{max}} + 1}$. For an $N$-chunk payload under this idealized i.i.d. baseline, the overall burst delivery success probability $P_{\mathrm{success}}$ is modeled as:
\begin{equation}
P_{\mathrm{success}} = \left(1 - p^{R_{\mathrm{max}} + 1}\right)^N, \qquad P_{\mathrm{fail}} = 1 - P_{\mathrm{success}}
\label{eq:burst_fail}
\end{equation}
For a lossy channel with a 20\% frame error rate ($p = 0.20$) and $R_{\mathrm{max}} = 5$ (matching \texttt{LoRaMultiPacketConfig::MAX\_RETRIES}), $P_{\mathrm{success}} = (1 - 0.20^6)^{20} \approx 99.87\%$ for a 20-chunk transfer. In physical wireless environments with correlated shadowing and reverse-link fading, overall completion rates are evaluated empirically via the stochastic ns-3 campaign in Section~\ref{sec:eval}.

\subsection{Memory Bounding and RAM Footprint Analysis}
To guarantee memory safety on constrained microcontrollers, the dynamic memory allocated for an active reassembly session at the receiver is strictly bounded by:
\begin{equation}
M_{\mathrm{session}} = S_{\mathrm{struct}} + N_{\mathrm{chunks}} \cdot S_{\max} + \left\lceil \frac{N_{\mathrm{chunks}}}{8} \right\rceil
\label{eq:ram_footprint}
\end{equation}
where $S_{\mathrm{struct}} \approx 48$~bytes represents the session tracking structure metadata, $S_{\max} = 244$~bytes is the maximum chunk stride, and the final term represents the binary \ac{SACK} bitmask.

For a representative 20-chunk payload (4.88~KB data size), a complete reassembly session requires $\approx 4.93$~KB of RAM (totaling $\approx 49.3$~KB across 10 concurrent 20-chunk sessions). On entry-level microcontrollers with limited SRAM ($\le 64$~KB), the concurrency pool ceiling ($\texttt{MAX\_CONCURRENT\_SESSIONS}$) is tuned to 1--2 sessions in \texttt{LoRaMultiPacketConfig}, while runtime heap protection (\texttt{AvailMem()}) prevents allocation failures by rejecting new requests with \texttt{CONN\_NACK(BUSY)} when memory is depleted.

\subsection{Formal Protocol Algorithms}
To ensure complete specification clarity and system-level reproducibility across different hardware platforms, Algorithm~\ref{alg:segmentation} and Algorithm~\ref{alg:reassembly} formally detail the transmitter-side segmentation pipeline and the receiver-side out-of-order reassembly engine, respectively.

\centering
\begin{minipage}[t]{0.485\textwidth}
\begin{algorithm}[H]
\caption{LAMP Payload Transmission and SACK-ARQ (Transmitter)}
\label{alg:segmentation}
\footnotesize
\begin{algorithmic}[1]
\Require Payload $P$ (size $L$), $dstAddr$, Max Chunk Size $S$, Mode $M$
\Ensure Delivery Status (\texttt{OK} or \texttt{FAIL})
\State $N \gets \lceil L / S \rceil$
\If{$N > 255$} \State \Return \texttt{ERR\_PAYLOAD\_TOO\_LARGE} \EndIf
\State $msgId \gets \text{GetNextMsgId}()$
\For{$i \gets 0$ \textbf{to} $N-1$}
    \State $cLen \gets (i == N-1) ? (L - i \cdot S) : S$
    \State $flags \gets (M \in \{\text{Mode 3}, \text{Mode 4}\} \textbf{ and } i == N-1) ? \texttt{FLAG\_ACK\_REQ} : \texttt{0x00}$
    \State $hdr \gets \text{BuildHdr}(src, dst, msgId, N, i, cLen, flags)$
    \State $crc \gets \text{CalcCRC16}(hdr, P[i\cdot S : i\cdot S + cLen])$
    \State $F_i \gets \text{SerializeFrame}(hdr, P[i\cdot S : i\cdot S + cLen], crc)$
    \State $\text{Transmit}(F_i)$
\EndFor
\If{$M \in \{\text{Mode 1}, \text{Mode 2}\}$} \State \Return \texttt{OK} \Comment{Unreliable delivery complete} \EndIf
\State $retries \gets 0$; $lastIdx \gets N - 1$
\While{$retries \le R_{\mathrm{max}}$}
    \State $sack \gets \text{WaitForSack}(T_{\mathrm{timeout}})$
    \If{$sack == \text{TIMEOUT}$}
        \If{$retries == R_{\mathrm{max}}$} \State \textbf{break} \EndIf
        \State $\text{Transmit}(F_{lastIdx})$; $retries \gets retries + 1$
    \ElsIf{$\text{IsAllAcked}(sack.bitmap)$}
        \State \Return \texttt{OK} \Comment{Full payload delivery confirmed}
    \Else
        \If{$retries == R_{\mathrm{max}}$} \State \textbf{break} \EndIf
        \State $missing \gets \text{MissingChunks}(sack.bitmap)$
        \For{$idx \in missing$}
            \State $cLen \gets (idx == N-1) ? (L - idx \cdot S) : S$
            \State $flags \gets (idx == \text{Last}(missing)) ? \texttt{FLAG\_ACK\_REQ} : \texttt{0x00}$
            \State $hdr \gets \text{BuildHdr}(src, dst, msgId, N, idx, cLen, flags)$
            \State $crc \gets \text{CalcCRC16}(hdr, P[idx\cdot S : idx\cdot S + cLen])$
            \State $F_{idx} \gets \text{SerializeFrame}(hdr, P[idx\cdot S : idx\cdot S + cLen], crc)$
            \State $\text{Transmit}(F_{idx})$
        \EndFor
        \State $lastIdx \gets \text{Last}(missing)$; $retries \gets retries + 1$
    \EndIf
\EndWhile
\State \Return \texttt{ERR\_MAX\_RETRIES\_EXCEEDED}
\end{algorithmic}
\end{algorithm}

\footnotesize
\begin{algorithmic}[1]

\State $(hdr, payload, crc) \gets \text{ParseFrame}(F)$
\If{$\text{ValidateCRC}(hdr, payload, crc) == \text{FAIL}$} \State \text{Drop}($F$); \Return \EndIf
\If{$hdr.dstAddr \neq myAddr \textbf{ and } hdr.dstAddr \neq \texttt{0xFF}$} \State \text{Drop}($F$); \Return \EndIf
\If{$hdr.dstAddr == \texttt{0xFF} \textbf{ and } (hdr.flags \ \& \ \texttt{FLAG\_ACK\_REQ})$} \State \text{Drop}($F$); \Return \EndIf
\If{$hdr.totalChunks == 0 \textbf{ or } hdr.chunkIndex \ge hdr.totalChunks$} \State \text{Drop}($F$); \Return \EndIf
\If{$\text{IsCompleted}(hdr.srcAddr, hdr.msgId)$}
    \If{$hdr.flags \ \& \ \texttt{FLAG\_ACK\_REQ}$} \State $\text{SendTerminalSack}(hdr.srcAddr, hdr.msgId)$ \EndIf
    \State \text{Drop}($F$); \Return
\EndIf
\State $session \gets \text{FindSession}(hdr.srcAddr, hdr.msgId)$
\If{$session == \text{NULL}$}
    \If{$\text{AvailMem}() < hdr.totalChunks \cdot S_{\max}$} \Comment{Safe stride check}
        \State \text{SendNack}(hdr.srcAddr, \texttt{BUSY}); \Return 
    \EndIf
    \State $session \gets \text{AllocBuf}(hdr.totalChunks, S_{\max})$
\EndIf
\State $idx \gets hdr.chunkIndex$
\If{$\text{IsBitSet}(session.bitmap, idx)$}
    \State \text{Drop}($F$) \Comment{Duplicate chunk, ignore write}
\Else
    \State $\text{WriteChunk}(session.buffer, idx \cdot S_{\max}, payload)$
    \State $\text{SetBit}(session.bitmap, idx)$; $session.count \gets session.count + 1$
\EndIf
\If{$hdr.flags \ \& \ \texttt{FLAG\_ACK\_REQ}$}
    \State $\text{SendSack}(hdr.srcAddr, hdr.msgId, session.bitmap)$
\EndIf
\If{$session.count == hdr.totalChunks$}
    \State $P \gets \text{ExtractPayload}(session.buffer)$
    \State $\text{DeliverToApp}(P)$; $\text{MarkCompleted}(hdr.srcAddr, hdr.msgId)$; $\text{FreeSession}(session)$
\EndIf
\end{algorithmic}
\end{algorithm}

\subsection{Session Control and Handshake Protocol}
To support stateful stream negotiation and protect resource-constrained receivers from buffer overflows, LAMPv2 introduces a \ac{3WHS} mechanism.

\subsubsection{Three-Way Handshake Procedure}
As illustrated in Figure~\ref{fig:3whs_sequence}(a), the connection lifecycle follows a three-step exchange:
\begin{enumerate}
  \item \textbf{SYN}: The initiator sends a \texttt{SYN} control frame (\texttt{FLAG\_CONN\_REQ}) addressed to the target node's \texttt{dstAddr}, containing a 4-byte \texttt{SynMetadata} payload (\texttt{requestedPayloadSize}, \texttt{windowSize}, \texttt{timeoutMs}).
  \item \textbf{SYN-ACK}: Upon receiving the \texttt{SYN}, the peer evaluates available memory and protocol version. If accepted, it responds with a \texttt{SYN-ACK} control frame (\texttt{FLAG\_CONN\_REQ | FLAG\_CONN\_ACK}) addressed back to the initiator. The receiver clamps \texttt{acceptedPayloadSize} to its maximum buffer capability.
  \item \textbf{ACK}: The initiator parses the \texttt{SYN-ACK}, adopts the negotiated payload size, and transmits a final \texttt{ACK} frame (\texttt{FLAG\_CONN\_ACK}). Both nodes transition their internal state machine to \texttt{ESTABLISHED}.
\end{enumerate}

\subsection{Concurrency and Fault Handling}
To ensure protocol stability in multi-node and lossy environments, LAMP incorporates the following fault-handling mechanisms:
\begin{itemize}
  \item \textit{Simultaneous Connection Resolution}: If two nodes transmit \texttt{SYN} frames to each other simultaneously, a deterministic tie-breaking rule resolves the conflict: the node with the lower numerical \texttt{NodeAddress} yields and transitions back to \texttt{CLOSED}, while the node with the higher \texttt{NodeAddress} proceeds with session setup.
  \item \textit{Receiver Busy Rejection}: If a receiver receives a \texttt{SYN} frame while its active reassembly session is already locked by another node, it responds with a \texttt{CONN\_NACK} frame (\texttt{FLAG\_CONN\_NACK}) specifying a \texttt{BUSY} status code, causing the requester to back off.
  \item \textit{Source Address Filtering}: Initiators in \texttt{waitForSynAck} and \texttt{waitForSack} validate incoming control frames against the expected \texttt{srcAddr}, ignoring packets from unrelated third-party nodes.
  \item \textit{Incomplete Handshake Timeout}: If a \texttt{SYN-ACK} or \texttt{ACK} of a \ac{3WHS} is lost in transit, the receiver in \texttt{SYN\_RCVD} or initiator in \texttt{SYN\_SENT} automatically aborts and resets to \texttt{CLOSED} after an inactivity timeout (\texttt{timeoutMs}).
\end{itemize}

\section{Preliminary Proof of Concept}
\label{sec:poc}
An initial prototype using commercial Ebyte E220-series modules validated the core segmentation concept. Field trials confirmed feasibility but exposed three limitations: (1)~the modules exposed a proprietary network layer that prevented direct control of physical-layer parameters; (2)~a large, unoptimized application header inflated per-chunk airtime; and (3)~no acknowledgment or retransmission mechanism was available.

These findings motivated the redesign on Semtech SX126x-class transceivers via the RadioLib driver, validated on Heltec Wi-Fi \ac{LoRa}~32~V3 boards. The revised implementation described in the following sections, is fully hardware-agnostic through the \ac{HAL} interface and incorporates the 9-byte Logical Header, \ac{CRC}-16 integrity checks, and the \ac{SACK}-based retransmission mechanism.

\section{Hardware Level Implementation}
\label{sec:implementation}
To validate the proposed protocol, a complete implementation of the LAMP library was developed in C++17. The design is modular, separating the transport state machine from physical hardware dependencies and parameter policies.

\subsection{Centralized Configuration and Parameter Decoupling}
To eliminate hardcoded constants and enable deterministic tuning across heterogeneous embedded targets, all protocol operational parameters are centralized within a dedicated compile-time configuration namespace (\texttt{LoRaMultiPacketConfig}). This design encapsulates three primary domains:
\begin{itemize}
  \item \textbf{Memory and Concurrency Limits}: Governs maximum concurrent reassembly sessions (\texttt{MAX\_CONCURRENT\_SESSIONS} = 10, reducible to 1--2 on memory-constrained Cortex-M0/AVR devices), physical FIFO buffer bounds (\texttt{PHY\_BUFFER\_SIZE} = 256~bytes, reflecting transceiver hardware FIFO capacity supporting the 255-byte maximum LoRa PHY payload cap), and completed sequence deduplication depth (\texttt{MAX\_COMPLETED\_HISTORY} = 16).
  \item \textbf{Timing and Retransmission Policies}: Configures the default retry ceiling ($R_{\mathrm{max}} = 5$), minimum SACK timeout floor ($T_{\min} = 1000$~ms, tunable for low-latency P2P links), safety multiplier ($\alpha = 1.5$), and half-duplex switching guard ($\delta = 25$~ms).
  \item \textbf{Session Lifecycle Thresholds}: Defines handshake initiation timeouts (\texttt{DEFAULT\_SYN\_TIMEOUT\_MS} = 3000~ms), connection inactivity teardown periods (\texttt{DEFAULT\_CONN\_INACTIVITY\_TIMEOUT\_MS} = 15000~ms), and stale session pruning timers (\texttt{PRUNE\_TIMEOUT\_MS} = 15000~ms).
\end{itemize}
Complementing the compile-time configuration, the \ac{3WHS} mechanism enables dynamic run-time parameter negotiation (\texttt{SynMetadata}), providing a two-tier flexibility model that adapts to variable channel conditions and peer memory capabilities.

\subsection{Hardware Abstraction Layer (\ac{HAL})}
To keep the protocol core hardware-agnostic, a clean \ac{HAL} interface (\texttt{RadioLibHal}) was implemented. On the physical nodes, the concrete class \texttt{EspHal} wraps ESP32-S3 hardware resources: \ac{SPI} Communication (register configuration and \ac{FIFO} buffer transfers for the Semtech SX1262), \ac{GPIO} Interrupts (NSS, RST, BUSY, and the DIO1 RX/TX completion interrupt pin), and Timing Primitives (\texttt{millis()} and \texttt{delay()}).

\subsection{Host-Based Unit Testing}
Following a \ac{TDD} methodology, the protocol core was validated in isolation on a desktop host using the \textbf{Unity} framework in PlatformIO, verifying: (i) Modbus \ac{CRC}-16 calculation on headers and partial/padded payloads, (ii) reassembler state transitions under out-of-order and duplicate chunk arrivals, and (iii) deterministic pruning of stale session descriptors.

\subsection{Physical Benchmarking Setup}
Physical validation was conducted using two Heltec Wi-Fi \ac{LoRa}~32~V3 development boards (ESP32-S3 + Semtech SX1262) configured with: Carrier Frequency 869.525~MHz, SF7, BW 500.0~kHz, CR 4/5, TX Power +10~dBm, and 8-symbol preamble.

\subsubsection{Regulatory Compliance and Regional Deployment}
It is important to clarify the relationship between the LAMP transport protocol and RF regulatory constraints. LAMP operates strictly at the \textit{transport layer} and is agnostic to regional carrier frequency, channel width, and RF power limits; compliance with these constraints is the responsibility of the underlying MAC/PHY layer.

Under European ETSI~EN~300~220-2 regulations~\cite{etsi300220}, the 869.400--869.650~MHz sub-band (Band P) allocates a 250~kHz total frequency block permitting up to 10\% duty cycle and an output power up to 500~mW ERP (27~dBm). For field deployments strictly adhering to this sub-band, channel bandwidths of $\le 250$~kHz (specifically 125~kHz or 250~kHz raster centered at 869.525~MHz) are selected. To characterize the protocol's upper theoretical throughput limits under maximum channel stress, our simulation campaign and laboratory benchmarks evaluated a wideband configuration ($BW = 500.0$~kHz, matching standard US915 / AU915 wideband LoRa allocations) on an experimental carrier.

Additionally, the reference C++ library provides opt-in MAC-layer helpers, including SX1262-native Channel Activity Detection (CAD) with randomized exponential backoff (CSMA-CA) and duty-cycle pacing to mitigate channel contention. These features are decoupled from the transport core and offered as convenience primitives for integrators targeting shared ISM spectrum.

\section{Performance Evaluation and Experimental Methodology}
\label{sec:eval}
To evaluate the reliability, throughput, and communication limits of LAMP, we adopt a two-stage evaluation methodology: a large-scale stochastic network simulation campaign executed in ns-3, complemented by functional hardware testbed validation on microcontroller nodes and a planned outdoor field benchmarking campaign.

\subsection{Network Simulation Benchmarking (ns-3)}
\label{sec:ns3_eval}
To characterize protocol performance under controlled fading channels across extensive distance ranges, we developed a full C++ simulator integrated into the ns-3 framework (\texttt{ns3-lorawan}). The simulator reproduces the exact LAMPv2 frame structure (9-byte Logical Header + 2-byte \ac{CRC}-16), all four operational modes, the \ac{3WHS} handshake, and selective bit-vector \ac{SACK} retransmissions over a Nakagami-$m$ fast-fading propagation loss model calibrated for the Semtech SX1262 transceiver (+24.2~dBm EIRP, 869.525~MHz), with shape factors: $m = 3.0$ for \ac{LoS} (strong specular component), $m = 1.5$ for Urban (moderate multipath), and $m = 1.0$ for Rural (Rayleigh fading).

\subsubsection{Simulation Campaign Hierarchy}
To achieve statistical convergence, an extensive Monte Carlo campaign comprising 117,050 total independent simulation runs was conducted. The experimental space spans 3 RF propagation environments (\ac{LoS}, Urban, Rural), 3 Spreading Factors (SF7, SF9, SF10), 4 operational modes (Mode 1 to Mode 4), and 50 independent random seeds per parameter configuration across an adaptive distance grid extending dynamically up to 23.5~km with early-stopping thresholds once reception falls to 0\% across consecutive steps. Each curve point plotted in Figs.~\ref{fig:ns3_pdr} and~\ref{fig:ns3_goodput} represents the sample mean over 50 independent Monte Carlo seed replications for a representative $N=20$-chunk payload (4.88~KB data size), with shaded ribbons denoting 95\% confidence intervals.

\subsubsection{Analytical Reliability Bound under Stated Assumptions}
To model payload completion probabilities analytically, we define a theoretical baseline under stated hypotheses:
\begin{enumerate}
  \item \textit{Independent Loss Model}: Channel frame loss is modeled as an independent and identically distributed (i.i.d.) Bernoulli error process with packet error rate $p \in [0, 1)$ and error-free control feedback ($p_{\mathrm{SACK}} = 0$). While the i.i.d. Bernoulli model provides a tractable analytical baseline, physical \ac{LPWAN} channels typically exhibit temporally correlated fading.
  \item \textit{Bounded Repair Rounds}: Selective \ac{SACK} retransmissions are bounded by the protocol's maximum repair round budget $R_{\mathrm{max}} = 5$ (matching \texttt{LoRaMultiPacketConfig::MAX\_RETRIES}).
\end{enumerate}
Under these idealized assumptions, the analytical upper bound for successfully reassembling an $N$-fragment payload across $R_{\mathrm{max}}$ retries matches Eq.~(\ref{eq:burst_fail}):
\begin{equation}
P_{\mathrm{complete}}(N, p, R_{\mathrm{max}}) = \left( 1 - p^{R_{\mathrm{max}} + 1} \right)^N
\label{eq:analytical_bound}
\end{equation}
Because Algorithm~\ref{alg:segmentation} enforces a global session repair round budget ($R_{\mathrm{max}} = 5$) across all missing fragments rather than independent per-chunk retries, Eq.~(\ref{eq:analytical_bound}) serves as an optimistic theoretical baseline. Empirical multi-chunk delivery dynamics under correlated channel fading and joint forward-reverse link losses are directly evaluated via the stochastic ns-3 campaign.
It is crucial to clarify that when reliable modes (Mode 3 and Mode 4) sustain a 100\% Application Payload Delivery Ratio ($PDR_{\mathrm{app}}$) in Fig.~\ref{fig:ns3_pdr}, this does not indicate physical channel reliability or zero-loss propagation. Rather, it demonstrates that the selective bit-vector \ac{SACK}-\ac{ARQ} mechanism successfully recovers lost fragments within the $R_{\mathrm{max}} = 5$ retry budget prior to session timeout.

In \ac{LoS} conditions, SF10 sustains complete payload reassembly up to 19.1~km, exhibiting a steep drop-off between 20.0~km and 23.1~km as frame loss probability exceeds retransmission recovery budgets. Conversely, best-effort unreliable modes (Mode 1 and Mode 2) experience progressive packet drop rates as spatial fading degrades signal-to-noise ratios.

Fig.~\ref{fig:ns3_goodput} depicts effective application-layer Goodput (bps). While best-effort streaming (Mode 2) achieves peak throughput in pristine channels by omitting acknowledgment latency, Mode 4 (\textit{Reliable Stream}) preserves sustained throughput near physical channel capacity across the operational range, degrading only near receiver sensitivity thresholds.

\subsection{Planned Real-World Field Benchmarking Campaign}
\label{sec:field_benchmarking}
While hardware testbed experiments on two Heltec Wi-Fi \ac{LoRa}~32~V3 nodes have validated the functional correctness, C++ memory safety, \ac{3WHS} state machine transitions, and out-of-order reassembly of LAMP, a systematic outdoor field campaign is planned as future experimental work to record real-world empirical performance under environmental interference, multipath reflections, and temperature-induced frequency drift.

\subsubsection{Planned Experimental Matrix and Evaluation Metrics}
The planned outdoor physical validation strategy follows established \ac{LPWAN} characterization methodologies~\cite{cattani2017}. It will sweep transmission distances (1 to 5000~meters across \ac{LoS} and \ac{NLoS} conditions) and payload sequence sizes (1 to 100 chunks, $\approx 24.6$~KB) under standard radio configurations (SF7, BW 500~kHz, CR 4/5, 10~dBm TX power).

During the planned outdoor campaign, four core performance metrics will be recorded across 5 independent trials per operational mode: (i)~\textbf{Application Payload Delivery Ratio ($PDR_{\mathrm{app}}$)}, measuring successful reassembly rate; (ii)~\textbf{End-to-End Latency}, from initial serialization to reassembly completion; (iii)~\textbf{Effective Throughput (Goodput)}, calculated as delivered payload bits over elapsed duration; and (iv)~\textbf{Retransmission Overhead}, tracking extra frames and \ac{SACK} packets relative to unreliable baselines.

\section{Conclusion and Architectural Roadmap}
\label{sec:conclusion}
This paper presents the design, implementation, network simulation, and hardware validation of LAMP, a lightweight and reliable transport-layer architecture optimized for transmitting segmented large payloads over point-to-point and local multi-node \ac{LoRa} networks. By replacing traditional Stop-and-Wait per-packet acknowledgments with selective retransmissions requested via cumulative binary bitmaps, and eliminating redundant SOM/EOM markers in favor of implicit index derivation, the protocol achieves high reliability under lossy conditions with minimal airtime overhead and duty-cycle footprint.

\subsection{Protocol Scope and Limitations}
To provide a transparent systems assessment, three inherent architectural boundaries of baseline LAMPv2 are identified:
\begin{enumerate}
  \setlength{\itemsep}{1.5pt}
  \setlength{\parskip}{0pt}
  \item \textit{Session Capacity Boundary}: A single transport session is bounded to 255 chunks $\times$ 244~B = 62,220~bytes ($\approx 62.2$~KB). Larger files require application-layer multi-session chunking.
  \item \textit{Pessimistic Buffer Pre-allocation}: To guarantee memory safety against out-of-order partial tail chunks arriving first, the receiver allocates contiguous memory based on $N \times S_{\max}$ upfront. On RAM-constrained microcontrollers ($\le 32$~KB SRAM), the concurrency pool ($\texttt{MAX\_CONCURRENT\_SESSIONS}$) must be set to 1--2 sessions.
  \item \textit{Unauthenticated Baseline 3WHS}: Baseline LAMPv2 incorporates CRC-16 for physical frame integrity but omits cryptographic nonces. Consequently, adversarial replays of stale \texttt{SYN} frames could exhaust active session descriptors. This is mitigated via the opt-in Level-2 Security Profile (AES-128-GCM / HMAC) detailed below.
\end{enumerate}

\subsection{Architectural Roadmap}
To guide the long-term progression of LAMP from point-to-point data links to decentralized multiagent mesh networks, we define a three-level architectural roadmap:
\begin{itemize}
  \setlength{\itemsep}{1.5pt}
  \setlength{\parskip}{0pt}
  \item \textbf{Level 1 -- Addressed Transport \& Polite Spectrum Access (Current Stack)}: 8-bit addressing (\texttt{srcAddr}, \texttt{dstAddr}), 9-byte header, four operational modes, dynamic \ac{3WHS}, and opt-in CAD/CSMA-CA under ETSI~EN~300~220-1~\cite{etsi300220}.
  \item \textbf{Level 2 -- Adaptive Spectrum, Scheduling \& Security (Near-Term)}: Dynamic ADR tuning via RSSI/SNR metrics in \ac{SACK} feedback, time-slotted channel access (TDM)~\cite{wei2020tdm}, and an optional transport security profile (AES-128-GCM / HMAC-SHA256 with 32-bit replay counters).
  \item \textbf{Level 3 -- Multi-Hop Mesh \& IPv6 Extension (Long-Term Vision)}: Dynamic multi-hop routing (AODV-Light / RPL adaptation) with hop-by-hop vs. end-to-end \ac{SACK} reliability~\cite{kim2022multihop, wong2024mesh}, and 8-bit node ID mapping for IPv6 link-local bridging (\texttt{fe80::/64}).
\end{itemize}
